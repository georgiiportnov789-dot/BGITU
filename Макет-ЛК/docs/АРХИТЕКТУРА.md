## 1. Что именно строим

Из аудита видно, что это не «сайт-визитка», а три контура в одном продукте:

1. **Публичный сайт** — главная, институты, направления, абитуриенту, студенту, новости, документы, обязательный раздел «Сведения об образовательной организации».
2. **Личный кабинет** — дашборд, стипендия, расписание, оценки, задолженности, учебный план, портфолио, справки и заявления.
3. **Сервисы и интеграции** — ЭОС БГИТУ, Moodle, Госуслуги, 1С, SSO, ИИ-чат, генератор отчётов по ГОСТ, поиск, уведомления, аналитика.

Отсюда главное решение: **модульный монолит, а не микросервисы**. Один деплой, одна авторизация, общая БД и транзакции. Границы между разделами — папки-домены, а не сетевые вызовы. Отдельный сервис появляется только там, где действительно нужна другая нагрузка или другой стек (например, RAG-поиск на pgvector).

## 2. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Backend | Python 3.12+, Django 5 LTS | Уже есть Django-демо; знакомая команде среда; auth, admin, ORM, i18n, безопасность из коробки |
| CMS | Wagtail | Блочный редактор, версии страниц, черновики, согласование, роли — почти весь п. 3.4 аудита без самописной CMS |
| API | Django REST Framework | ЛК, мобильное приложение, интеграции, OpenAPI |
| БД | PostgreSQL 16 | Основная БД; полнотекстовый поиск; при необходимости pgvector для ИИ-чата |
| Очереди | Redis + Celery | Импорт ЭОС, рассылки, генерация документов, синхронизация расписания |
| Frontend | Django-шаблоны + Vite + HTMX/Alpine.js | Быстрый первый экран, SEO, доступность, минимум JS; сложные виджеты — точечно |
| Стили | CSS-токены + компоненты | Перенос текущей дизайн-системы (графит, бумага, safety-orange, Unbounded/Inter Tight/IBM Plex Mono) |
| Тесты | pytest + Playwright | Юнит/интеграционные тесты и живые сценарии студента/абитуриента |
| Инфраструктура | Docker Compose + nginx | Вуз/подрядчик сможет развернуть без Kubernetes |
| Документы | python-docx/docxtpl + WeasyPrint | ГОСТ-отчёты, справки, PDF |

Почему не Next.js/SPA на старте: публичному сайту нужны SEO, скорость и доступность, а не клиентский роутинг; ЛК с серверными шаблонами и точечным HTMX проще в поддержке и безопаснее. Если позже понадобится SPA, `apps/portal` можно отдать React-приложению через тот же `/api/v1/`, не перестраивая backend.

### 3.1. Что создавать сразу, а что позже

Дерево выше — целевое. Чтобы не плодить пустые папки, на первом этапе создаём только ядро:

- **Этап 1 (витрина):** `config`, `apps/core`, `accounts`, `cms`, `sveden`, `university`, `admissions`, `search`, `templates`, `frontend`, `docs`, `design`, `infra`.
- **Этап 2 (ЛК):** `education`, `schedule`, `portal`, `integrations/eos`, `integrations/sso`, `notifications`.
- **Этап 3 (сервисы):** `requests`, `reports`, `assistant`, `campus`, `analytics`, `integrations/moodle`, `integrations/gosuslugi`, `integrations/1c`.

## 4. Внутри одного домена

Каждый `apps/<домен>/` устроен одинаково — это и есть главный архитектурный шаблон:

```text
apps/schedule/
├── models.py           # Group, Lesson, Bell, Substitution
├── selectors.py        # чтение: выборки для страниц и API
├── services.py         # бизнес-логика: импорт, замены, iCal
├── api.py              # DRF: /api/v1/schedule/
├── urls.py
├── tasks.py            # Celery: синхронизация, напоминания
├── admin.py
├── templates/schedule/ # страницы домена
├── migrations/
└── tests/
```

Правила:

- **`models.py` не знает про ЭОС.** Внешние форматы живут в `apps/integrations/eos/`, преобразование — в `mappers.py`.
- **`selectors.py`** — только чтение и оптимизация запросов; **`services.py`** — операции и транзакции.
- **`api.py`** — тонкий слой, без бизнес-логики.
- Домены не импортируют модели друг друга напрямую: связь через `services`/`selectors` или общий `core`.
- Все внешние вызовы — в Celery-задачах с retry и идемпотентностью.

## 7. Этапы

1. **Витрина** — CMS, университет, приём, обязательный раздел, поиск, доступность. Результат: публичный сайт с редактируемым контентом.
2. **ЛК** — `accounts` + SSO, `portal`, `schedule`, чтение ЭОС, iCal. Результат: личный кабинет студента.
3. **Сервисы** — `requests`, `reports`, `assistant`, `notifications`, `campus`, `analytics`. Результат: портал с заявками, справками, ИИ-чатом и отчётами.

## 9. Открытые вопросы (до создания репозитория)

1. **Доступ к ЭОС**: есть ли API/веб-сервисы или только БД/выгрузки? Это главный риск сроков.
2. **Хостинг**: контур вуза или внешний? Нужны ли 152-ФЗ, локализация БД и резервное копирование.
3. **SSO**: БГИТУ ID своими силами или через существующий провайдер (Госуслуги/Keycloak)?
4. **ЛК**: серверные шаблоны достаточно или нужен SPA-кабинет?
5. **Языки**: только ru или ru + en для иностранных студентов?
6. **ИИ-чат**: облачная LLM или локальная модель в контуре вуза? От этого зависит `apps/assistant`.
7. **Команда**: кто поддерживает после сдачи — вуз, студенческая лаборатория, подрядчик?
